# 未定项（不预填立场，等生长逼出答案）

这里的每一条都**没有默认值**。遇到时必须显式选一边，选完把决定写回本文（连同当时的依据），不要默默按习惯走。

格式：`状态: 未定 | 已定(YYYY-MM-DD) · 决定 · 依据`

---

## q1 · 继承来的引导，副本有没有写权？

`状态: 未定`

- 有写权 → 必须同时配回流闸门（否则副本之间会漂成互不兼容的方言）
- 只读 → 副本只动状态，规则不合用时只能发提案等批，慢

当前 `spawn.py` 按**只读**拍副本（`RULES/.readonly` 标记），这是可逆的临时选择，不是结论。
决定时要想清楚：写权给出去容易，收回来难。

## q2 · 共享上下文继承多少？

`状态: 未定`

三档候选：
- 引导全继承 + 机制层全继承 + 主题基线全继承（同主题时最省事）
- 引导全继承 + 只继承 `portability: universal`（最干净，但每个副本要重新长领域机制）
- 引导全继承 + 机制层全继承 + 基线只继承骨架（当前 `MANIFEST.json` 的实现）

现有实现是第三档。是否放宽到第一档，等"换主题开第二个副本"时看实际成本再定。

## q3 · 移植是单向回流还是双向？

`状态: 未定`

- 单向（副本 → 原初库）：安全，但原初库的机制改进永远到不了老副本
- 双向：老副本能吃到改进，但会被人从背后改写路径（尤其改到 `fork.md` 的评分权重时，同一轮算出来的优先级会变）

`RULES/context.md` 当前按单向写。开双向的前置条件建议：先有"机制版本对表"（`MANIFEST.lock`），能判断某个副本停在哪个机制版本。
